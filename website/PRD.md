## 1. 背景与目标

### 1.1 项目背景

本项目是一个**个人在线作品集**：把我自己独立完成的东西集中放在一个公开可访问的网站上，既展示成品的样子，也展示背后的技术实现。

要解决的问题很具体——现有的技术资产全部只存在于本机、只跑在命令行里，别人看不到，也无法体验。这个网站的作用，就是把这部分能力搬到公开网络上，让任何人点开链接就能看到、就能上手试。

需要明确的是：**这是一份由本人自己搭建、自己维护、自己对外展示的作品集合，不是商业项目，也不承载任何销售能力。**

现已存在的资产（均在本机 `/Users/husubing/Documents/AI项目经历/香薰客服/`）：

| 资产 | 内容 | 位置 |
|---|---|---|
| 商品数据 | 80 个 SKU，价格带 29.9–269 元，含香调/场景/人群/禁忌/卖点标签 | `信息资料/雾歇香薰_商品数据.xlsx` |
| 知识库原文 | 香薰蜡烛专业使用说明（Markdown） | `信息资料/香薰蜡烛产品使用说明.md` |
| 检索层 | 9 个 Python 模块：改写、混合检索、精排、切块、索引、落盘 | `knowledge_base/` |
| 构建产物 | FAISS 索引 + 切块 JSON + 元信息 | `kb_data/`（index.faiss / chunks.json / meta.json） |
| 评测集 | 香薰品类检索质量评测用例 | `信息资料/香薰品类AI客服RAG评测测试集.xlsx` |

当前知识库实测规模（来自 `kb_data/meta.json`，构建于 2026-10-10）：

- 向量维度：768（模型 `tongyi-embedding-vision-flash`）
- 切块数量：68
- 索引类型：FAISS `IndexFlatIP`（配合向量归一化，内积等价于余弦相似度）

现有检索链路（`knowledge_base/retriever.py`，这是网站要展示的核心技术）：

```
用户提问
  ↓
LLM 多路改写（deepseek-flash，生成 3 条规范查询）
  ↓
每路 query 并行做混合检索
  ├─ 向量语义召回（FAISS，768 维，余弦）
  └─ BM25 关键词召回（jieba 分词，k1=1.5 / b=0.75）
  融合方式：final = 1.0 × 向量分 + 0.25 × BM25 分（加法增强）
  ↓
多路结果 RRF 融合（倒数排名融合，平滑常数 K=60）
  ↓
gte-rerank-v2 交叉编码器精排（候选池 Top 20）
  ↓
返回 Top-K 知识块
```

### 1.2 项目目标（可衡量）

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G-01 | 访问者打开首页 3 秒内意识到"这里有 AI" | 首屏在 1 屏内出现 AI 客服入口，无需滚动 |
| G-02 | 访问者能在不注册、不下载的前提下试用 AI 客服 | 从落地到发出第一个问题，点击次数 ≤ 2 |
| G-03 | 链接在国内网络环境可正常打开 | 手机 4G 网络实测打开时间 < 3 秒 |
| G-04 | 全站移动端可用 | 375px 宽度下无横向滚动、无遮挡 |

**设计原则：作品集网站的成功指标是"信任"而不是"转化"。** 一切与"让人相信这是真做出来的"无关的功能，一律不做。

### 1.3 非目标（明确不做）

- 不做真实电商：没有购物车、支付、订单、库存
- 不做用户系统：没有注册、登录、个人中心
- 不做后台管理界面：所有内容直接固化在代码里
- 不做搜索引擎排名优化（SEO）
- 不做多语言
- 不接微信小程序
- 不做真实的品牌视觉资产拍摄（用现有素材 + 占位图先跑通）

## 2. 目标用户与使用场景

### 2.1 用户画像

## 6. 视觉与交互规范

### 6.1 视觉方向

延续商品标签中最高频的关键词：**木质、沉稳、东方**。整体不做香甜、不做少女、不做高饱和。

| 项目 | 规范 |
|---|---|
| 主色 | 低饱和墨绿或灰褐（具体色值在 M1 阶段定稿） |
| 背景 | 米白或浅灰，避免纯白刺眼 |
| 文字 | 深灰而非纯黑，正文行高 1.7 以上 |
| 中文标题字体 | 衬线（宋体一类），体现东方气质 |
| 正文字体 | 无衬线，保证可读性 |
| 圆角 | 克制使用，以直角或小圆角为主 |
| 阴影 | 不使用重阴影与发光效果 |

### 6.2 交互原则

| 原则 | 说明 |
|---|---|
| 动效克制 | 只做淡入与轻微位移，不做视差、不做滚动劫持 |
| 首屏无延迟 | 首屏不依赖任何远程图片加载完成 |
| 移动端优先 | 所有布局先确定 375px 下的表现，再放大到桌面 |
| 无弹窗拦截 | 不出现"订阅我们"之类的遮挡 |

## 7. 技术方案（初版，待定稿）

### 7.1 前端

| 方案 | 说明 | 取舍 |
|---|---|---|
| 纯静态 | 一个文件夹的 HTML/CSS/JS，无构建步骤 | 上手最快、出错概率最低，但工程话题度弱 |
| Next.js + Tailwind | 有构建流程与路由 | 工程话题度更强，但调试成本明显更高 |

> 该决策尚未做出，见第 12 章。

### 7.2 后端（最大的工程点）

当前 RAG 代码是本地 Python，**无法直接被浏览器调用**。需要新增一个 HTTP 服务层：

1. 用 FastAPI 把 `HybridRetriever` 包成一个接口，例如 `POST /api/chat`
2. 接口内部复用现有模块，不重写检索逻辑
3. 接口需要流式返回（Server-Sent Events），以支持 F-202

关键约束：**AGICTO 的 API Key 绝对不能出现在前端代码里**，必须由后端持有。

### 7.3 部署

| 层 | 候选 | 备注 |
|---|---|---|
| 前端 | Vercel / Cloudflare Pages / 国内对象存储 | 需评估国内访问速度（见 R-02） |
| 后端 | Railway / Render / 国内轻量云服务器 | 需支持常驻进程与 SSE |

流程：本地开发 → 推送 GitHub → 平台自动构建 → 获得公网地址。

### 7.4 成本控制

| 消耗点 | 说明 |
|---|---|
| Embedding 接口 | 每次提问触发 1 次向量化（改写后的多路 query 会放大调用量） |
| 改写模型 | 每次提问触发 1 次 deepseek-flash 调用 |
| 精排模型 | 每次提问触发 1 次 rerank 调用 |

按当前链路，**一次用户提问约产生 3 次模型调用**。公网暴露后必须配套限流与预算封顶。

### 7.5 Prompt 与指令规格

本网站自身采用 vibe coding 方式开发，站内运行的 AI 客服也是由 Prompt 驱动的。**这两件事都叫 Prompt，但完全不是一回事**，必须分开写：

| 类别 | 作用对象 | 什么时候用 | 存在形式 |
|---|---|---|---|
| 开发期 Prompt | 喂给编程 AI，用来生成页面代码 | 开发阶段，反复调整 | 对话记录（应当留存） |
| 运行期 Prompt | 喂给 AI 客服，规定它怎么回答 | 用户每次提问时随请求发送 | 后端代码里的系统提示词常量 |

#### 7.5.1 开发期 Prompt：项目级上下文（新开会话先贴这一段）

```
你正在帮我开发「雾歇香薰」个人在线作品集网站，项目目录 /Users/husubing/Documents/AI项目经历/香薰客服/website/。

技术栈：纯静态 HTML/CSS/JS，无构建步骤。未确定前不要引入任何框架、npm 包、CDN 依赖。
设计基调：低饱和、东方木质调、克制。标题用系统宋体族，全站配色不超过 3 种。
页面只有三个：/ 首页、/demo AI 客服、/about 关于我。

硬性约束：
1. 绝对不要在任何前端文件里出现 API Key、Token 或任何密钥。
2. 不要引入 jQuery / React / Tailwind CDN / 图标字体库。
3. 不要修改 knowledge_base/ 目录下的任何 Python 文件。
4. 中文文案不要有机器翻译感，不要堆感叹号，不要使用 emoji。
5. 每次只改我指定的那一个文件。改完先用一句话说明：改了什么、没改什么。
```

> 这一段的作用是**让 AI 每次都站在同一个上下文里**。vibe coding 最常见的失败不是"AI 不会写"，而是"AI 不知道你的项目是什么"，于是每次都按它默认的技术栈猜一套，前后不一致。

#### 7.5.2 开发期 Prompt：按里程碑拆分

| 阶段 | 目标 | Prompt 要点 |
|---|---|---|
| M1 首页 | 跑通结构与视觉基调 | 只做首屏 Hero + 品牌故事 + 产品系列 + 页脚；产品卡片用占位图；这一轮不做任何交互 |
| M2 客服页 | 接通后端 | 先用一段固定的假应答跑通前端交互，接口处留 TODO，这一轮不要同时改样式 |

> **一次只让 AI 做一件事。** 让它"把整个网站做出来"，产出的必然是一堆互相引用不上的文件。

#### 7.5.3 运行期 Prompt：AI 客服系统提示词（初版草稿）

这一段才是真正决定客服表现的东西，应作为常量放在后端：

```
你是「雾歇香薰」的在线顾问，只回答与香薰产品、使用方法、安全注意事项相关的问题。

规则：
1. 只依据检索到的产品资料回答。资料里没有的，直接说"这个我不确定"，不要编造。
2. 涉及孕妇、婴幼儿、宠物、过敏、疾病的问题，一律提示"谨慎使用，建议咨询专业人士"，不给出肯定结论。
3. 不承诺价格、库存、发货时间、赔偿金额，不执行任何退款操作。
4. 不回答与香薰无关的闲聊，礼貌地把话题引回产品。
5. 回答控制在 3 句话以内，口语化，不要罗列要点。

语气：克制、温和，像一个懂香的人，不像促销员。
```

#### 7.5.4 注意事项

1. **不要把两类 Prompt 混在一个文件里。** 开发期 Prompt 属于过程记录，运行期 Prompt 属于产品代码，混在一起极易改错对象。
2. **每次生成后必须自己读一遍改动。** vibe coding 最大的风险是"看起来能跑"，但 AI 可能顺手删掉了上一轮已经做好的功能——本项目的既定要求是保留原有实现逻辑，不做覆盖式重写。
3. **报错时把完整报错原文贴给 AI**，不要自己转述。转述会丢掉最关键的行号信息。
4. **运行期 Prompt 每改一次，都要同步更新第 5.2 节的行为描述**，否则文档和线上表现会对不上。
5. **开发期 Prompt 应当留存。** 它是作品集的一部分——能证明页面是在你的主导下逐步生成的，而不是一次性套模板套出来的。

#### 7.5.5 自查

- [ ] 开发期 Prompt 里写明了"不要引入框架"和"不要出现 API Key"吗？
- [ ] 运行期 Prompt 覆盖了孕妇、婴幼儿这类高风险问题吗？
- [ ] 运行期 Prompt 里写了"资料里没有就说不确定"吗？
- [ ] 每次 AI 生成代码后，是否真的读过改动，而不是只信它说的"已完成"？

| 编号 | 风险 | 影响 | 对策 |

| R-01 | 公网暴露后端后，第三方刷接口导致 API 账单失控 | 高 | 按 IP 限流；设置接口调用预算上限；必要时改为"预设问题 + 每日少量自由提问" |
